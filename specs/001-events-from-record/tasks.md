# Tasks: Observability Events, One Trusted Record of What Happened

**Input**: design documents in `specs/001-events-from-record/`: spec.md (53 allocated requirement numbers, REQ-169 and REQ-184 withdrawn; User Stories 1 to 8; three NEEDS CLARIFICATION items), plan.md (Record versus code items 1 to 22; Constitution Check; Complexity Tracking), research.md (R-01 to R-18 and four plan proposals), data-model.md, contracts/event-envelope.md, contracts/status-header.md, contracts/read-interface.md, contracts/intake-from-projects.md, contracts/alerts-to-living-documents.md, contracts/harness-receipts.md, quickstart.md.

**Prerequisites**: plan.md and spec.md (both present). The stack constitution in `.specify/memory/constitution.md` (1.0.5) applies. The older component constitution at the repository root (`constitution.md`) stands as additions under it, with its first principle in conflict and held (H-12).

**Scope**: the events part is built in this repository, on the existing collector (plan.md, Structure decision; the code home is held, H-1). Where plan.md records a behaviour as existing, the task is test only. The existing suite covers no clause of this spec (plan.md, Constitution Check III; quickstart.md), so no row of the coverage table is "built and tested".

**Tests**: required. Constitution III: the failing test is written and seen to fail before the code that makes it pass. Every build task depends on the task that writes its failing test. Tests run on fixtures in `tests/fixtures/` (made-up names, placeholder machine identities, a fixture clock, a fixture gateway, a fixture Living Documents intake, fixture Harness receipts), never against the operator's live store or live sessions. Checks the record asks for on a real machine are acceptance checks and are OPERATOR tasks.

**Implementation gate**: nothing here starts before the operator's review that names this project (constitution, workflow step 5), and not while analysis.md reports a CRITICAL finding (workflow step 4).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel with other [P] tasks of the same phase (its own files, no dependency on an unfinished task of that phase).
- **[USnn]**: the spec's User Story nn. Setup, Foundational and Polish tasks carry no story label and name their requirements in the text.
- Every task names the requirements it serves (REQ-nnn), its repository-relative files and its check.
- **OPERATOR**: done only by the operator, on a real machine (credentials, the installed service, real harness hooks, a real second machine). No agent does these tasks.

## Path conventions

Existing directories are kept and extended (plan.md, Project Structure). The events service is `apps/observability/` with the new folders `readers/`, `watchdog/` and `read-interface/`; shared types and value sets are `shared/`; the shared adapter client and the new producer state, buffer, redaction, machine identity and project identity modules are `adapters/shared/`; published forms are `forms/`; documents are `docs/`. New tests are `tests/*.test.ts` with fixtures in `tests/fixtures/`, run by `bun test` from the repository root with the existing three test files. "The suite passes" below means `bun test` from the repository root exits 0 with no failing test.

## Dependencies and Execution Order

### Phase dependencies

- **Setup (Phase 1)**: T001 first; the other setup tasks after it, in parallel.
- **Foundational (Phase 2)**: needs T002. Settings, envelope, vocabulary, producer state, machine identity and the Reading can run side by side; the store needs the envelope and settings; the intake needs the store; the watchdog runner needs the store.

- **Polish**: after the stories it names; T135 is last.
- **OPERATOR tasks** wait on the operator and block only the tasks that name them. T041 sits in US02 but runs after the deployment T134 of the Polish phase.

### Cross-story dependencies

- The read interface (T025, US01): needed by US03 (T054, T059, T061), US04 (T063, T065, T073, T075), US06 (T097), US08 (T112, T113, T119, T124).
- The adapters on the new envelope (T036, US02): needed by US05 (T081, T091), US06 (T095, T105), US07 (T107).
- The local buffer (T057, US03): needed by US04 (T067) and the deployment (T134).
- Gap records (T066, US04): needed by US07 (T109).
- Staleness (T031, US01): needed by US08 (T122).
- Redaction (T082, US05): needed by US07 (T110).
- The login request (T084, US05): needed by US08 (T119).
- Agent figures (T098, US06): needed by US08 (T124).
- The tool call report of US03 (T060) is built on fixture tool call events before US06 records them (T106); T106 reruns T059.
- The P1 story US01 reads values that US02 to US04 produce; its tests use fixture stores, so it can be built first.

### Within each story

- The failing test is written and seen to fail before its build task starts.
- A test-only task is first run against a stand-in that breaks the behaviour (patched inside the test run only), so it is seen to fail (constitution III), then against the real code.
- A test-only task that fails against the real code shows that plan.md's "exists" claim is wrong: the failure is recorded on the task, a build task is added after it, and the test is not weakened.
- An existing test whose expectation changes is named in the commit with the requirement that changes it; a failing check is never weakened.

### Parallel opportunities

- Test tasks marked [P] write their own test file and can run beside the others of their phase.
- `apps/observability/read-interface/answers.ts` is edited by many build tasks; two such tasks never run at once, even in different stories. The same holds for `apps/observability/server.ts`, `adapters/shared/obs-client.ts`, `extension/pi-observability.ts`, `apps/observability/db.ts` and `apps/observability/watchdog/rules.ts`.
- Readers (`apps/observability/readers/`) and watchdog modules other than `rules.ts` are independent of each other.
- Setup tasks after the baseline, and the foundational test tasks, are independent of each other.
